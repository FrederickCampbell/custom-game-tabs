# Custom Game Tabs engineering and interaction audit

Audit date: 14 November 2026. Baseline: `f7c861fe0a19995d401cabb3361a4812ed43a88d` (2.2.2). Implementation: branch `audit/input-lifecycle-polish`.

**Live-test correction:** the initial implementation below exposed input-timing, tooltip-ordering and sidebar-density regressions. See [PR #5 regression follow-up](PR5_REGRESSION_FOLLOWUP.md) for the corrected design and additional tests. The original 52-test result is historical, not live acceptance.

## Scope and confidence

Reviewed all 23 production Java files (7,293 baseline lines), configuration, build and packaging, resources, existing tests, README, changelog, and repository instructions. Retrieved the complete public issue collection: four open issues, no closed issues, one issue comment, and no repository pull requests. Reviewed the Plugin Hub submission/update discussions (#14531, #15371, #16613), current RuneLite input/overlay/widget APIs, Compact Orbs, and Interface Layout. Public searches did not uncover additional attributable feedback. Private communities and unreported installations are outside this evidence.

This is a source audit plus executable headless regression testing, not an exhaustive proof of correctness. No RuneScape input was automated and no live account was used. UI screenshots are Swing test fixtures, not live-client captures. “Reproduced” below means a deterministic source trace or automated test; user reports are explicitly distinguished. Live acceptance remains required, especially for game scripts and interactions with other plugins.

References below give baseline file/line locations; files are under `src/main/java/com/freddy/customgametabs/` unless stated otherwise. ## Architecture and mathematical reasoning

Use one coordinate system: RuneLite logical canvas coordinates. Stretched Mode already maps input as `xLogical = floor(xPhysical / scaleX)` and likewise for Y. Repeating the transform would double-scale; bypassing it creates the reported phantom target. Independent X/Y scales matter when aspect ratio is unlocked. OverlayRenderer already provides dock dragging and saved positions; CGT only owns gestures needing multi-overlay group semantics.

Rendering publishes an immutable set of rectangles. Input reads a completed snapshot instead of reconstructing geometry from independently changing origins and dimensions. Empty snapshots explicitly represent unavailable surfaces. Rectangle hit testing is O(n), with n at most 14; a spatial tree would increase complexity without a useful payoff. A before-render invalidation favors passing input through over retaining an invisible target when a layer disappears. This short unavailable interval must still be checked under live rendering load.

For a run with available extent A, button size c and gap g, capacity is `max(1, floor((A + g) / (c + g)))`, with the drawer handle included in the occupied sequence. Wrapping provides bounded layout without shrinking icons or changing stored settings. Dock column adaptation solves the equivalent rows/height constraint. Ordinary layouts retain their prior geometry.

For snapping, minimizing `dx² + dy²` gives the same ordering as Euclidean distance without square roots. Sticky connectivity among 14 buttons needs only 91 unordered pair comparisons. Keep that simple bounded algorithm. No calculus, graph index, background worker, or generalized layout engine is justified here.

The five snapshot slots (three presets, working, recovery) bound cache memory. Comparing stored strings before parsing avoids stale caches after external edits. Parsing drawer membership once removes repeated splitting/allocation per traversal. These are operation-count improvements; no FPS, latency, allocation-rate or CPU percentage claim has been measured.

## UI/UX evaluation and design direction

Retain RuneLite's dark sidebar, native tab iconography and existing color settings. Changing the visual vocabulary would impose relearning without addressing reported failures. The implemented sidebar gives each tab a readable label above its state/reorder controls; Main, Drawer and Hidden are explained where the choice is made. Disabling the drawer now explains why its assigned tabs are unavailable. Responsive wrapping keeps controls reachable instead of silently losing them beyond the viewport.

The [Nielsen Norman usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) support visible state, familiar conventions, recognition, and recovery. CGT already has Save/Load and Restore Previous Layout; preserve them. A future explicit edit mode could show drag affordances and selected sticky groups, but requires a clear state/escape design and real-user validation before adding another mode.

[W3C target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) and [visible-focus guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) are useful design references, not a claim that Swing or a game overlay conforms to web WCAG. Larger reorder targets and accessible names improve the editor. Existing 25% scale and zero-opacity choices are retained for compatibility; tiny/invisible configured buttons remain a user-selected accessibility risk. Recommend normal-size controls and readable opacity in documentation, rather than silently rewriting saved preferences. Color is not the only state cue in the sidebar. Actual contrast under custom colors, screen-reader operation, keyboard focus after every rebuild, and client/UI scaling need manual assessment.

## Known limitations and unresolved findings

* **Medium: presets omit dock position.** `CustomGameTabsPlugin.java:1737` captures freeform coordinates and drawer position, while RuneLite persists the dock position globally. README's former “complete setup” wording overpromised. Documentation now specifies this limitation. A future versioned snapshot field can store dock position while treating absent legacy data as “keep current”; this audit does not silently migrate schemas.
* **Medium: competing native-widget owners.** Interface Layout's tab customization and CGT can manipulate the same STONE widgets. Identity-safe restoration prevents writing an obsolete widget, but cannot arbitrate two active owners. Disable one plugin's tab-management feature during acceptance. Compact Orbs and other minimap/layer modifiers require the matrix below; blanket compatibility is not established.
* **Medium: initialization report and Combat/sailing report remain partly unresolved.** Tests validate forwarding to the current widget and lifecycle cancellation, not the current game's script execution. Record live backing widget ID, action label and exception if these reports persist. Avoid a hardcoded script/tab-index workaround without that evidence.
* **Medium: oversized freeform groups and newly seeded tabs.** The canonical snapshot preserves group spacing, but native per-overlay clamping can still distort an impossible-to-fit group on-screen. New-tab seeding also independently clamps near edges. A follow-up needs an explicit overflow policy, not silent scaling or destructive saved-coordinate changes.
* **Low: legacy drawer-placement heuristic.** `CustomGameTabsPlugin.java:1968` baseline includes a positional guess for the old default handle. An intentionally matching position can be indistinguishable. Address with a migration marker/schema change after defining how existing users are recognized.
* **Maintainability:** the plugin coordinator remains large. Next useful extractions are gesture ownership, layout editing transactions, and drawer placement. Shared button drawing can later be consolidated once live rendering behavior is accepted. Splitting classes solely to reduce line count would not improve correctness.

## Verification, compatibility and delivery plan

The original baseline passed 32 tests despite E01. The revised suite passes **52 tests, zero failures/errors** on Temurin Java 11.0.33, Gradle 8.10, released RuneLite 1.13.6. Command: `./gradlew --no-daemon clean test jar`. In this execution environment, the equivalent Gradle 8.10 binary used a temporary loopback Maven mirror to populate dependencies and then ran offline; repository/build source dependencies were unchanged. Ordinary upstream networking remains covered by the added workflow when run on GitHub.

The standard jar contains only plugin classes/resources; all 34 class files use Java 11 bytecode (major 55). Mockito and Byte Buddy are test dependencies, including the test JVM's startup agent; they are not in the standard Plugin Hub jar. The optional pre-existing development shadowJar combines test/runtime dependencies and is not the Hub artifact. `git diff --check` passes. Config group and persisted keys are unchanged; v1/v2/v3 preset parsers and existing migration behavior are retained. No server, telemetry, production reflection, process launching, input injection, or `client.menuAction` was added.

[Plugin Hub review](https://github.com/runelite/runelite/wiki/Plugin-Hub-Review) checks security and rule compliance; it explicitly does not certify correctness, performance or plugin conflicts. The [restricted-features list](https://github.com/runelite/runelite/wiki/Rejected-or-Rolled-Back-Features) and [Hub build instructions](https://github.com/runelite/plugin-hub) were reviewed. Existing native OnOp activation was retained, consistent with the plugin's original [review discussion #14531](https://github.com/runelite/plugin-hub/pull/14531). This work is not a new approval from RuneLite or Jagex.

Implementation priorities:

1. **Implemented:** repair coordinate pipeline, stale hit regions, queued gestures and lifecycle guards; preserve native widget operations.
2. **Implemented:** deterministic animation, viewport-aware drawer/dock geometry, sprite overrides, usable sidebar; bounded parsing/cache improvements and redundant-path removal.
3. **Implemented:** behavioral regression coverage, Java 11 packaging verification, CI, and accurate documentation.
4. **Required before release:** execute [manual acceptance matrix](MANUAL_TEST_PLAN.md), especially the reported sailing and first-login behavior. Capture failures without changing multiple plugins simultaneously.
5. **Follow-up with evidence:** dock-position snapshot migration, deliberate overflow recovery, conflict ownership policy, and focused coordinator extraction. Re-run the acceptance matrix after any such architectural change.
6. **Release only after acceptance:** merge reviewed changes, choose release version, then update the Hub descriptor to the accepted commit. No Hub update or merge is part of this audit's verification claims.
